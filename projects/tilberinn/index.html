Summary

This was our last group project at The Game Assembly. This time we had very free hands in what to make, so we chose to make a first-person zombie shooter with Call of Duty: Zombies as reference. We also wanted the game to have online co-op.

For this project, I spent most of my time on the networking for co-op. Since our engine was never made with networking in mind, I had to build everything from the connection up to syncing gameplay between players. In the end we had to scrap co-op, since not everything worked in time and I was mostly working on it alone.

I also worked on our Unreal tools. I added RGB mask export from Unreal to our engine, a Play From Here option to start the game where you clicked in the level, and did more fine-tuning on the export plugin and the shader preset tool for the technical artists.

Networking

Since our reference game was Call of Duty: Zombies, we wanted to have online co-op. The problem was that our engine was not planned or built for networking, so everything had to be added on top of systems that expected the whole game to run on one machine.

Connection

Image: diagram of host and clients, or a code screenshot

For the connection, I used UDP with Asio, since it has good wrappers for the Winsock functions. One player hosts the game and the other players connect to the host’s address.

Receiving runs on its own thread and puts the packets in a queue. The game then reads the queue once every frame on the main thread. This made it so the rest of the engine didn’t have to care about threads.

When a player joins, the client sends a connect message to the host. The host answers with a network ID for the client and then sends out to all players who is in the game. When the level is loaded, each client tells the host it is ready, and when all players are ready the host sends a final sync of the players and the enemies.

Since UDP doesn’t guarantee that a message arrives, the client tries to connect a few times with a timeout before it gives up.

Messages

Image: code screenshot of registering a message

Every packet starts with a message type. In the gameplay code, you register a function for a message type together with the struct it should receive. When a message arrives, the message handler reads the struct from the packet and calls the function.

I also made it possible to send a message straight into our event system. For example, when a door is opened, it is sent over the network and the other players get the same OpenDoor event as if it happened in their own game.

To read and write the structs, I made a serializer that uses structured bindings to go through the members of a struct. This made it so a new message only needed a new struct, without writing any extra code to send it.

This was based on what I learned during my specialization, where I made a message dispatcher and a payload registry for a similar problem.

Replication

Image: code screenshot of NetworkedComponent

To make it easier to network more parts of the game, I made a base class called NetworkedComponent. A component that inherits from it has to say how its state is packed and how a received state should be applied. When something changes, the component marks itself as dirty.

Each networked component also has authority. Only the one with authority sends its state, and the other players apply it. For example, the local player has authority over their own character.

I also made a replication manager that keeps track of all networked components by network ID and component type. At the end of every frame, it takes all dirty components with authority and sends them together in one batch. When a batch is received, it finds the right component for each update and applies the state.

Syncing the game

Video: two players in the same game

With the replication in place, I could start syncing the players’ movement and animations. For the animations, I only sent the values that drive the animation, like movement direction, if the player is sprinting and which weapon they are holding. The animations are then played locally in each player’s game.

The enemies were harder, since there are a lot of them and they come from a pool. Instead of sending every enemy’s position every frame, I worked on sending what each enemy is doing and who it is targeting, so each player’s game could simulate the movement from that.

Unreal Tools

RGB masks

Image: the same model with different colours from a mask

The graphics artists wanted more ways to set the scene without making new textures for every variation of a model.

To solve this, I added support for exporting RGB masks from Unreal to our engine. Each channel in the mask marks a part of the model that can get its own colour. This made it possible to use the same model or static object with different colours around the level, and made it easier for the artists to add more decoration.

Play From Here

Video: Play From Here in Unreal

To test something in a level, you had to start the game from the beginning and walk to the place you wanted to test.

I added a Play From Here option in Unreal that boots the level in our engine and places the player where you clicked. This made it a lot faster to test specific parts of a level.

Export plugin and shader presets

I continued to fine-tune the export plugin and the shader preset tool that I made in earlier projects. This made it so the technical artists didn’t have to write the shader pipeline settings by hand.

I also helped another team member with how to get Unreal’s Sequencer working with our engine.

Conclusion

Adding networking to an engine that wasn’t made for it showed me how much networking affects the rest of the code. Things like who owns what, who has authority and what needs to be sent have to be decided early, and systems that were made for one player have to be changed to work with more.

Even though co-op didn’t make it into the game, I learned a lot from building it from the connection up to syncing gameplay. The tools work also made the workflow from Unreal to our engine smoother for the artists.
